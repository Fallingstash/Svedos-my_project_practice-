# 🎧 Svedos

> **«Сведи сам свой трек»**

## 💔 Проблема: Паралич выбора и Стерильность
Каждый начинающий музыкант (рэпер, битмейкер, гитарист) сталкивается с одним и тем же: он слышит, что трек звучит плохо, но не знает, как прийти к лучшему результату. Нет какого-то осознавания действия в физике, мы просто действуем эмпирически. 
Современный рынок предлагает два пути:
1. **YouTube:** Часы общих туториалов, которые не работают на *твоем* конкретном миксе.
2. **Автоматические сервисы (Ozone, LANDR):** «Черные ящики», которые делают звук громче, но убивают душу трека, усредняя его под общий шаблон.

## 💡 Наше решение: Svedos
 **Интерактивный наставник**. 
Мы объединили математику цифровой обработки сигналов (DSP) и доступность больших языковых моделей(LLM), что позволяет новичку понять физику процесса простым языком. 

Svedos не делает работу за вас — он учит вас, как ее сделать. Мы исповедуем принцип **Artistic Exemption (Уважение к замыслу)**: если вы хотите мрачный, басовый звук — ИИ не будет заставлять вас делать «попсовую» яркость. Он лишь подскажет, как убрать грязь, сохранив ваш уникальный вайб.

## 🧠 Методология: Как это работает под капотом?
Мы верим, что ИИ должен быть переводчиком, а не волшебником. 

1. **Математика (Python/Librosa):** Нейросеть не слышит звук. Сначала наш Python-скрипт раскладывает аудиофайл через **Быстрое Преобразование Фурье (FFT)** на частоты. Он измеряет LUFS, True Peak, фазовую корреляцию и находит частотные пики (проблемные зоны).
2. **Интерпретация (LLM/OpenRouter):** Мы передаем эти «сухие» цифры языковой модели. Ее задача — перевести сложные термины (`High Pass на 30 Гц`, `Crest Factor`) в человеческие ощущения: *«бубнит», «глухо», «вата», «звук из-за стены»*.
3. **Действие:** Пользователь получает визуальный график, понятный совет от ИИ и сам вносит правки в свою DAW (например, в FL Studio).

## 🚀 Ключевые фичи (MVP)
*   **Анализ мастер-трека и стемов:** Загружайте готовый микс или отдельно бит и вокал (для поиска частотных конфликтов).
*   **Интерактивные карточки метрик:** Наводите на показатели (LUFS, фаза, динамика) и читайте подробные объяснения с привязкой к плагинам.
*   **Умные промпты:** ИИ учитывает жанр, сегменты трека (куплет/припев) и ваши мысли о треке («замысел»).
*   **Сравнение версий:** Загрузите новую версию после правок, и система покажет прогресс на графике «До/После».
*   **История сессий:** Сохранение диалогов с возможностью переключения между разными треками.

## 🛠️ Технологический стек
*   **UI:** Streamlit
*   **DSP (Audio Analysis):** Librosa, NumPy, SciPy, Pyloudnorm
*   **AI Integration:** OpenAI SDK (через OpenRouter API)
*   **Database / audio:** SQLite + local files for development; Supabase PostgreSQL + private Storage in production.
*   **Безопасность:** Ограничение размера файлов, Rate Limit от спама, защита от Prompt Injection.

## Хранение данных и восстановление

Локальная разработка использует SQLite (`history/svedos.db`) и локальные файлы
`history/<id-сессии>/`. Задайте `SVEDOS_DATA_DIR`, чтобы выбрать другой каталог.
Production использует только Supabase PostgreSQL и приватный bucket
`svedos-audio`; при `SVEDOS_ENV=production` отсутствие настройки Supabase
останавливает запуск, а ошибки соединения не переключают backend на SQLite.
Новая production-база должна быть пустой: импорт локальной `history/` не
поддерживается и автоматически не выполняется.

### Настройка production

1. Создайте проект Supabase в панели управления Supabase.
2. В **Project Settings → API** скопируйте Project URL и `service_role` key.
   Service role — секрет сервера; не используйте его в браузере или публичном
   клиенте.
3. В **Project Settings → Database → Connection string** получите URI для
   PostgreSQL. Используйте подходящий для хостинга connection mode/port и
   храните пароль только в secret manager.
4. В **SQL Editor** откройте
   `supabase/migrations/202611190001_svedos_storage.sql` и выполните миграцию
   на чистой базе. Она создаёт таблицы, ограничения и приватный bucket.
5. Задайте перечисленные ниже secrets в настройках развернутого приложения.
   Для локального запуска можно скопировать `.env.example` в `.env` и заменить
   заполнители. `.env` игнорируется Git; не вставляйте секреты в чат.
6. Запустите приложение и проверьте его status/health. Проверка старта
   обращается к PostgreSQL и проверяет существование и приватность bucket.
   Перед приглашением пользователей выполните User Flows нового/возвращающегося
   гостя, публикации, отзыва ссылки и удаления тестовой сессии с аудио.

Переменные окружения (значения в Git не добавлять):

| Имя | Назначение |
|---|---|
| `SVEDOS_ENV` | Установить `production` на production-хостинге. |
| `SVEDOSSTORAGEBACKEND` | В production обязательно `supabase`; локально `local`. |
| `SUPABASEDBURL` | Серверная строка подключения к PostgreSQL. |
| `SUPABASE_URL` | Project URL Supabase для Storage API. |
| `SUPABASESERVICEROLE_KEY` | Привилегированный ключ, только серверная среда. |
| `APPBASEURL` | Публичный базовый URL приложения для share-ссылок. |
| `GUESTCOOKIESECRET` | Случайный секрет подписи guest-cookie, минимум 32 байта в production. |
| `API_KEY` | Серверный ключ OpenRouter. |
| `SVEDOS_DATA_DIR` | Только local: необязательный каталог SQLite и аудиофайлов. |

Для Streamlit Secrets задайте те же имена как TOML верхнего уровня в
`.streamlit/secrets.toml` (локально) или в панели Secrets хостинга:

```toml
SVEDOS_ENV = "production"
SVEDOSSTORAGEBACKEND = "supabase"
SUPABASEDBURL = "<postgres connection URI>"
SUPABASE_URL = "<Supabase Project URL>"
SUPABASESERVICEROLE_KEY = "<server-only service role key>"
APPBASEURL = "<public app URL>"
GUESTCOOKIESECRET = "<long random secret>"
API_KEY = "<OpenRouter key>"
```

Для проектов на Streamlit host внесите каждую пару ключ/значение в раздел
**App → Settings → Secrets**. Не коммитьте `.streamlit/secrets.toml`.

Для проверки реального Postgres + Storage задайте перечисленные Supabase-переменные
в локальном окружении и выполните
`python -m unittest discover -s tests -p test_supabase_integration.py -v`.
Интеграционный тест создаёт сессию и временный файл со случайными ID, затем
проверяет owner access, метрики, share/revoke, аудио и удаление. Запускайте его
только на отдельном тестовом проекте: при отсутствии конфигурации он будет
пропущен, а не заменён mock-успехом.

Гостевой ID хранится в подписанной HMAC-cookie сроком на год. Сервер проверяет
подпись при каждом новом контексте; гостевые сессии изолированы по ID.
Публичная ссылка создаётся владельцем явно, а в базе хранится SHA-256-хеш
токена. Публичный доступ только для чтения.

Cookie устанавливается используемым Streamlit cookie-компонентом из браузера;
его API не поддерживает флаг `HttpOnly`. `Secure`, `SameSite=Lax`, срок
действия и HMAC-проверка уменьшают отдельные риски, но HMAC не защищает cookie
от кражи или повторного использования при XSS. Не помещайте в cookie данные
сессии или другие секреты.

## Установка и запуск

Создайте виртуальное окружение, установите зависимости из `requirements.txt`,
настройте `GUESTCOOKIESECRET` и `API_KEY`, затем запустите
`streamlit run app.py`. Ограничения загрузки: 100 МБ и 20 минут; обработка также
ограничена размером декодированного аудио для защиты памяти.
